# 모임 계좌·거래내역 API

## 범위와 구현 상태

이슈 #34의 MVP는 계좌 연결·정보 조회·해제, 수동 거래 동기화, 저장된 거래내역 조회다.
`bank` 도메인에서 제공하며 실제 송금, 자동 납부 매칭, 정기 동기화는 구현하지 않는다.
운영진이 거래내역을 확인한 뒤 기존 정산 수동 납부 API로 납부를 기록한다.

공식 계약: [Bank API 문서](https://bankapi.co.kr/docs), [요금제·제한](https://bankapi.co.kr/pricing).
2026-11-10 확인한 계약에 맞춰 NH·KB·WR·IBK 빠른조회와 SH 로그인 기반 조회를 지원한다.
실제 계좌 연결을 위한 은행별 빠른조회 등록 등의 사전 준비는 계좌 소유자가 수행해야 한다.

## 권한·보안

- 모든 API는 JWT 쿠키 인증이 필요하다.
- **계좌 정보·거래내역 GET은 해당 모임의 모든 활성·미삭제 회원에게 공개한다.** 회계 투명성을 위해 일반 회원도 조회한다.
- 연결·해제·동기화는 활성 OWNER/MANAGER만 수행한다. 계정과 모임 회원이 삭제되면 접근할 수 없다.
- 폐쇄·삭제·삭제 이력이 있는 모임은 접근할 수 없다. 모임이 없으면 404, 해당 권한이 없으면 403이다.
- POST·DELETE는 CSRF 쿠키와 `X-XSRF-TOKEN` 헤더가 필요하다. 먼저 `GET /api/v1/auth/csrf` 응답의 `result.token`을 사용한다.
- 교차 출처 요청은 `credentials: 'include'` 또는 `withCredentials: true`가 필요하다.
- API Key·Secret Key·원본 계좌번호는 AES-256-GCM 암호문으로 보관한다. 인증 태그에 레코드별 컨텍스트를 결합한다.
- 계좌번호는 응답에서 끝 4자리만 표시한다. 예금주명은 운영진 입력값이며 은행이 확인한 예금주 인증 결과가 아니다.
- 계좌 비밀번호·생년월일/사업자번호·인터넷뱅킹 ID/PW는 **동기화 요청에서만 받아 저장하지 않는다.**
- 연동 요청 DTO의 문자열 출력과 JSON 직렬화에서 비밀정보를 제외한다. 잘못된 JSON 예외 로그에도 입력값을 포함하지 않는다.
- 은행의 원본 오류 본문·예외 메시지는 클라이언트에 전달하지 않는다.

## 엔드포인트

기본 경로: `/api/v1/groups/{groupId}/bank-account` (`groupId` 양수)

| 메서드 | 하위 경로 | 권한 | 성공 코드 |
| --- | --- | --- | --- |
| POST | 없음 | OWNER/MANAGER | 201 / BANK201_1 |
| GET | 없음 | 모든 활성 모임 회원 | 200 / BANK200_1 |
| DELETE | 없음 | OWNER/MANAGER | 200 / BANK200_2, result=null |
| POST | `/sync` | OWNER/MANAGER | 200 / BANK200_3 |
| GET | `/transactions?page=0&size=20` | 모든 활성 모임 회원 | 200 / BANK200_4 |

모든 성공 응답은 프로젝트의 `{isSuccess, code, message, result}` 형태다. 미연결 계좌의 GET은 404 / BANK404_1이다.

### 1. 계좌 연결

```json
{
  "bankCode": "NH",
  "accountNumber": "12345676789",
  "accountHolder": "예금주명",
  "apiKey": "발급받은-API-Key",
  "secretKey": "발급받은-Secret-Key"
}
```

은행 코드는 NH·KB·WR·IBK·SH, 계좌번호는 하이픈 없는 숫자 8~20자리다.
키는 200자 이하의 공백·콜론 없는 ASCII 문자열, 예금주명은 50자 이하다.
은행 호출 없이 로컬 연결을 저장한다. 실제 키/계좌 조회 가능 여부는 동기화에서 확인한다.
한 모임에 활성 연결 하나만 허용한다. 같은 은행·계좌번호는 다른 모임에 중복 연결할 수 없다.
키를 교체하려면 해제 후 다시 연결한다. 같은 모임에 같은 계좌를 다시 연결하면 기존 거래를 보존하여 재사용한다.
해제 후 재연결해도 계좌의 조회 제한 시각은 초기화하지 않는다.

연결·정보 조회의 `result`:

```json
{
  "accountId": 1,
  "bankCode": "NH",
  "accountNumberMasked": "*******6789",
  "accountHolder": "예금주명",
  "lastSyncedAt": null,
  "nextSyncAt": null,
  "lastSyncError": null
}
```

연결 해제는 인증정보의 암호문을 제거하고 연결을 소프트 삭제한다. 거래내역은 삭제하지 않는다.
동기화가 진행 중이면 409이다. 해제 상태에서는 현재 연결 조회가 404이며, 같은 계좌를 재연결하면 이전 거래도 다시 조회된다.
다른 계좌로 바꾸기 전 계좌의 거래는 DB에 보존하지만, 이전 연결 선택·조회 UI/API는 후속 범위다.

### 2. 수동 동기화

개인 계좌(NH·KB·WR·IBK):

```json
{
  "startDate": "2026-11-01",
  "endDate": "2026-11-10",
  "accountPassword": "1234",
  "residentNumber": "800101",
  "accountType": "personal"
}
```

사업자는 `accountType=business`와 사업자번호 10자리를 전달한다.
은행별 뒷자리 변환은 Bank API가 처리한다. 신한은 다음 형태를 사용한다.

```json
{
  "startDate": "2026-11-01",
  "endDate": "2026-11-10",
  "accountPassword": "1234",
  "loginId": "은행-로그인-ID",
  "loginPassword": "은행-로그인-비밀번호"
}
```

시작일·종료일 모두 포함하여 최대 31일, 종료일은 오늘까지다. 이 기간 제한은 MoEASY의 요청 크기 관리 정책이며 Bank API의 공식 최대 기간이라는 뜻은 아니다.
은행 응답은 최대 10,000건까지 원자적으로 저장하며, 응답 오류·비정상 금액·지원하지 않는 형식이면 전체 저장을 취소한다.
실제 입출금 시각은 한국 현지 시각으로 보관한다. `YYYY-MM-DD`, `YYYY/MM/DD` 거래일과 음수 잔액을 지원한다.
금액은 양의 Long 정수이며 소수·문자열 금액·범위 초과는 거부한다.

성공 `result` 예시:

```json
{"insertedCount": 12, "lastSyncedAt": "2026-11-10T10:00:00"}
```

- 동일 계좌는 요청을 시작한 후 최소 5분 동안 다시 호출하지 않는다. 성공뿐 아니라 실패에도 대기 시간을 적용한다.
- Redis에서 최근 30분 동안 API 키별·이 서버 전체 각각 30건의 **시도**로 제한한다. 실제 공급자의 성공 30건/요청 60건 제한보다 보수적인 정책이다.
- 여러 모임이 같은 키를 사용해도 카운터를 공유한다. 서로 다른 서버가 같은 공인 IP를 쓰는 경우의 요청은 로컬 카운터로 모두 알 수 없으므로 공급자의 429도 처리한다.
- 429의 `retryAfterSec` 또는 `Retry-After`를 반영한다. 정보가 없으면 30분 대기한다. 화면에서 자동 재시도하지 말고 계좌 정보의 `nextSyncAt`을 다시 읽는다.
- Redis가 사용 불가하면 은행을 호출하지 않는다. 요청을 자동으로 재시도하지 않는다.
- 연결 대기 5초, 응답 대기 70초다. 동기화 준비/완료에만 짧은 트랜잭션을 사용하며 HTTP 호출 중 DB 잠금을 유지하지 않는다.
- DB에 동기화 토큰·2분 임대를 기록한다. 병렬 요청은 409, 중단 후 임대가 만료되어도 기존 5분 제한은 유지한다.
- 성공 시에만 `lastSyncedAt`을 갱신한다. 실패해도 저장된 거래와 마지막 성공 시각은 유지하고 `lastSyncError`에 정규화된 오류 종류를 남긴다.
- 은행 통신·응답 오류는 은행 오류로, DB 저장 실패 등 예상하지 못한 내부 오류는 `500 / COMMON500_1`로 구분한다. 내부 오류의 `lastSyncError`도 `COMMON500_1`이다. 권한 등 기존 공통 오류는 해당 코드를 유지한다.
- 내부 오류에도 이미 설정된 계좌 호출 대기 시간은 유지한다. 실패 정리 중 오류가 발생하면 최초 응답 오류를 보존하고 동기화 임대 만료로 복구한다.
- 진단 로그에는 모임 ID·실패 단계·예외 종류·스택 위치만 기록하며, 예외 및 원인 예외의 메시지·요청/응답 본문·인증정보는 기록하지 않는다.
- 동기화 도중 운영진 권한이 사라지면 저장을 거부한다. 동기화만으로 납부 기록을 만들지 않는다.

### 3. 저장된 거래 조회

기본 페이지 0, 크기 20(1~100), 거래 시각 내림차순 → ID 내림차순이다.
DB만 조회하므로 화면 새로고침이나 페이지 이동으로 Bank API 호출 횟수가 소모되지 않는다.

```json
{
  "items": [{
    "transactionId": 10,
    "type": "DEPOSIT",
    "transactedAt": "2026-11-10T09:15:00",
    "description": "입금",
    "displayName": "",
    "counterparty": "홍길동",
    "amount": 10000,
    "balance": 150000,
    "branch": "",
    "memo": ""
  }],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1,
  "hasNext": false
}
```

은행이 거래 ID를 제공하지 않으므로 `거래 시각·종류·금액·잔액`의 SHA-256와 동일 행의 발생 순번으로 중복을 구분한다.
조회 날짜 전체를 받는 응답에서 같은 금융 행이 두 번 등장하면 두 건을 보존하고, 같은 기간을 재조회해도 다시 추가하지 않는다.
메모·표시명 변경은 별도 거래로 만들지 않는다. 공급자가 일부 거래를 누락하거나 금융 필드를 사후 정정하면 완벽한 식별을 보장할 수 없으며 수동 납부와 자동 연결하지 않는다.

## 배포 설정과 마이그레이션

`BANK_API_ENCRYPTION_KEY`에 Base64로 인코딩한 임의의 32바이트 키를 서버 환경변수로 설정한다.
예: `openssl rand -base64 32`로 생성하고 저장소·채팅·로그에 남기지 않는다. JWT 키와 별개의 키를 사용한다.
미설정 상태에서도 기존 기능은 기동되지만 은행 인증정보를 저장/복호화하는 동작은 503이다.
기존 `deploy/compose.yml`의 `env_file: .env`로 전달할 수 있다.

`BANK_API_BASE_URL` 기본값은 `https://api.bankapi.co.kr`이며 로컬 모의 서버 검증에만 변경한다.
암호화 키는 여러 서버에서 동일해야 하고 백업·보존해야 한다. 키가 바뀌면 기존 암호문과 계좌 지문을 사용할 수 없으므로
운영에서 단순 교체하지 말고 별도 재암호화·지문 이관 절차를 진행해야 한다.
실제 은행 호출은 국내 IP가 필요하다. Vercel 프론트가 공급자를 직접 호출하지 않고 라즈베리파이 또는 AWS 서울의 백엔드를 거친다.

기존 3개 은행 테이블에 암호문·인증 컨텍스트·동기화 상태와 활성 모임당 한 계좌 제약을 추가한다.
`secret_ref` 계열에는 `db:<컨텍스트 UUID>` 식별자만 저장하며 AWS Secrets Manager를 사용하지 않는다.
이미 기존 은행 테이블에 데이터를 수동 등록했다면 적용 전 모임별 활성 계좌 중복을 정리해야 한다.
기존 참조만 있는 레거시 연결은 암호문이 없으므로 동기화할 수 없고 해제 후 재등록해야 한다.

## 검증과 실제 계좌 확인 범위

`BankApiIntegrationTest`는 실제 MySQL·Redis·HTTP 클라이언트로 연결/해제, 권한, 중복·실패·CSRF를 확인한다.
Postman 모의 서버 재현 방법은 `postman/simulations/bankapi/bankapi.context.md`에 있다.
모의 검증은 실제 은행의 계좌 인증 성공·빠른조회 등록·국내 IP 허용을 증명하지 않는다.
운영진의 실제 키와 계좌는 테스트에 사용하지 않았으며 배포 후 별도 확인이 필요하다.
